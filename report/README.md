# Report Directory Guide

This directory holds the evaluation reports for the Torvalds skill: how well each model reviews code with and without the skill. Every `.md` file here is generated by a script — never edit them by hand (see [docs/CONTRIBUTING.md](../docs/CONTRIBUTING.md)).

## Which file answers which question

| Question | File | Generated by |
|---|---|---|
| Did the skill help each model find bugs? | [comparison.md](comparison.md) | `report/build_comparison.py` |
| Which model + skill pairing detects bugs best overall? | [cross_matrix.md](cross_matrix.md) | `scripts/render_cross.py` |
| What did model X report, reviewing with the skill? | [review-gpt-oss-120b.md](review-gpt-oss-120b.md) | `report/run_review.py` |
| What did model X report without the skill? | [baseline/review-baseline-gpt-oss-120b.md](baseline/review-baseline-gpt-oss-120b.md) | `report/run_review.py` |

Suggested reading order: `comparison.md` first (headline verdicts), then `cross_matrix.md` (generalization across pairings), then the individual `review-*.md` files when you need the full finding text.

## The review files

`run_review.py` makes each model review [antirez/smallchat](https://github.com/antirez/smallchat) (~700 LOC of C) using that model's own skill variant:

- `review-gpt-oss-120b.md`
- `review-glm5.2.md`
- `review-mistral-small-4-119b.md`
- `review-qwen3.8-27b.md`

Each file has YAML front matter (model, files reviewed, finding count, verdict) followed by findings grouped by source file, each with severity, type, location, issue description, and proposed fix. The `baseline/` subdirectory holds the same four reviews produced without any skill; `comparison.md` needs both arms.

## comparison.md

Answers: **does adding the skill help or hurt each model?** It aggregates the eight reviews above (four with the skill, four baseline) into per-model metrics, verdicts, consensus between models, and ground-truth benchmark scores. DS (Detection Score) is the primary metric; judge scores only break ties.

## cross_matrix.md

Answers: **which reviewer model + skill combination detects bugs best?** It covers all 4×4 pairings, written `A × B`: reviewer model A reads the code using the skill distilled by B (`A × A` is the native pairing). It includes baseline rows and a consensus analysis. Built from `data/eval_results.jsonl` and `data/eval_results_cross.jsonl`.

## Shared concepts

- **Reviewer model** — the LLM that reads the code and produces findings.
- **Skill** — the distilled Torvalds review-skill variant applied to the reviewer.
- **Judge model** — GLM5.2, rates review quality on a 0–2 scale per axis. It does not affect DS and may favor itself as a reviewer.
- **DS (Detection Score)** — combined precision/recall against ground-truth bugs; the metric that drives every ranking.
- **Evaluation provenance** — reviewer prompts never contain the ground-truth bug list, so numbers measure detection, not transcription.

## Regenerating

Run from the repository root:

```bash
python3 report/run_review.py         # all eight reviews; skips existing, --force redoes
python3 report/build_comparison.py   # comparison.md
python3 scripts/render_cross.py      # cross_matrix.md
```

`run_review.py` calls the LLM APIs and needs credentials (see [README.md](../README.md)); the two renderers only re-parse committed data and are cheap.

## Other files

`metrics.jsonl`, `decisions.jsonl`, `benchmark_matches.json`, `chunks/`, `.review_state.json` — generator byproducts (run state, timing metrics, chunked prompts, benchmark match records). Not reports; no need to read them.
